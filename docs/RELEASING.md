# Releasing Glissform

Main-branch pushes and pull requests run CI build checks without creating an installer or updating the feed. Version tags run those checks within the release workflow. The tag-only [release workflow](../.github/workflows/release.yml) creates one new `Glissform-<VERSION>.dmg` for each new version tag, attaches an internal copy to that tag's GitHub Release, uploads the public DMG and checksum to `glissform.app/downloads/`, then publishes its signed entry at `glissform.app/updates/appcast.xml`. Existing alpha.1–alpha.9 tags are source-only history; do not move or reuse them.

The workflow uses a standard GitHub-hosted macOS runner, a private GitHub Release for the tag's notes and backup assets once the source repository is private, and a public HTTPS site for downloads and updates. Private-repository Actions usage counts against GitHub's monthly allowance and may be billed beyond it. The app uses Sparkle's EdDSA key to verify the feed and exact downloaded DMG; it does not require an Apple Developer ID certificate. This does not make the app Apple-notarized or remove macOS's first-open warning.

## One-time setup

1. Keep the Glissform Sparkle private key in a safe backup. The public half is in [`config/sparkle-public-key.txt`](../config/sparkle-public-key.txt). The private half was generated in the local Keychain under account `glissform`; never commit it or paste it into a log, issue, or chat.
2. Export the private key using Sparkle's `generate_keys --account glissform -x <secure-file-outside-repo>` and set the GitHub Actions repository secret `SPARKLE_EDDSA_PRIVATE_KEY` to the file's contents. Remove the temporary export after checking the secret is set. The release workflow derives its public half and refuses to publish if it differs from the app's embedded key.
3. Keep `glissform.app` pointed at the release VPS and its HTTPS certificate renewing. The VPS has a `glissform-deploy` account that can write only the `downloads` and `updates` directories; Sparkle's private key stays off the VPS. Add the dedicated deploy private key as the GitHub Actions repository secret `GLISSFORM_DEPLOY_SSH_KEY`. The VPS host key is pinned in [`config/release-known-hosts`](../config/release-known-hosts); update that file only after verifying an intentional server replacement.
4. Ensure the repository's Actions settings allow `GITHUB_TOKEN` to publish GitHub Releases. The release job requests `contents: write`; it does not push an update branch.

## Each release

1. Choose a new public version in `VERSION` and a strictly larger numeric `BUILD_NUMBER`. Move only the changes shipping in this version from **Unreleased** to a matching `## <VERSION>` entry in `CHANGELOG.md`. Review README, ROADMAP, app guide, and issue tracker for release accuracy.
2. Run `bash scripts/build.sh --release` and `bash scripts/test.sh --release` on the intended source. The default build is the separate red **Glissform Dev** app and must never be packaged as a public release. Complete the physical beta checks in [`docs/TESTING.md`](TESTING.md), including lid, sleep/wake, screen access, and both update modes. Build a local DMG with `bash scripts/make-dmg.sh`; mount it, copy the app to a fresh test location, and check first launch and permissions on the development Mac.
3. Commit and push the release source to `main`. Normal pushes still publish no DMG. Create and push a new annotated tag `v<VERSION>` pointing to that exact commit. This is the step that authorizes and starts the release workflow; never move an existing public tag.
4. Wait for **Package version tag** to pass. Check the GitHub Release page for the exact tag, target commit, version-specific notes, prerelease status for alpha/beta/rc, and its backup DMG and checksum assets. Verify the public DMG and checksum at `https://glissform.app/downloads/` and the signed appcast at `https://glissform.app/updates/appcast.xml`. Test an upgrade from the prior installed release on the development Mac before calling the update path verified.

If packaging, signing, or upload fails, the workflow leaves the GitHub Release as a draft. It publishes the appcast only after the versioned public DMG and checksum have been uploaded and verified. A failed step can be retried, but an already published asset must match the rebuilt bytes; never silently replace a released DMG or move its tag. Keep older DMGs available for existing installations. Report and repair a failed release rather than declaring it complete.

## Installer appearance

Newly packaged installers use the release app's compiled icon for the mounted disk and the local `.dmg` file. The mounted disk icon is embedded in the image and survives downloads. The `.dmg` file icon is Finder metadata outside the image's data; ordinary HTTP downloads from GitHub or the website do not preserve it. This packaging change is unreleased and does not alter existing published installers.

The installer opens a Finder icon view with 720 × 400 starfield artwork, a **Welcome to Glissform** heading, drag-to-Applications instructions and curved white arrow at 60% opacity. The app and Applications shortcut remain real Finder items. Both labels have white pill-shaped backings for contrast. Finder renders native filenames in black when a custom background is used; the white labels shown in the concept preview are not supported by this standard Finder installer. The window's title bar, labels and icon appearance follow macOS; Finder can show path/status bars or filename extensions according to the user's preferences. Background artwork and layout are maintained in [`Artwork/Installer`](../Artwork/Installer); packaging renders 1× and 2× artwork into an embedded TIFF and writes the Finder layout without launching Finder.

Packaging needs Python 3.7 or later with `venv` and downloads the hash-pinned build tools in [`scripts/dmg-requirements.txt`](../scripts/dmg-requirements.txt) into the ignored `build/dmg-tools` environment. These tools are not shipped in the app or installer. To inspect a packaging change without replacing a versioned local DMG, use `bash scripts/make-dmg.sh build/Glissform-installer-preview.dmg` after the release app build. Check the mounted window and drag targets before shipping the next version.

## Installation and update limits without Developer ID

Users download a release DMG, drag Glissform into Applications, and try to open it. macOS may block this ad-hoc signed, unnotarized app on first launch. A user who trusts this specific download can use **System Settings → Privacy & Security → Open Anyway** after the blocked attempt. Glissform's Screen Recording permission may need to be granted again after an ad-hoc signed update because the code identity changes between builds. Do not promise a silent first install, a warning-free update, or uninterrupted screen permission.

With Automatic updates on, Sparkle checks the signed feed, downloads a newer eligible DMG, and normally installs when Glissform quits. If permission is required or the app stays running for a long time, Sparkle can show a prompt. With Automatic updates off, checks continue; a detected eligible update appears in the existing sidebar card and its **Update** button starts Sparkle's standard installation flow. The menu bar’s **Check for Updates…** command and the **Check for updates…** button in **Privacy & about** start a user-requested check in either mode. Alpha, beta, and release-candidate builds can receive prerelease updates; stable builds receive stable releases.
